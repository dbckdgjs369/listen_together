# 같이 듣기 (listen-together)

친구 2~4명이 **각자 자기 이어폰으로 같은 소리를 듣는** 앱. 이어폰 한쪽씩 나눠 끼는 걸 대체하는 게 목표다.

호스트(안드로이드)가 재생 중인 오디오를 `AudioPlaybackCapture` 로 가로채 로컬 네트워크에 뿌리고,
참여자는 **브라우저로 접속하거나**(설치 불필요) 이 앱으로 듣는다.

> PoC 단계다. Java, 외부 의존성 없음.

## 동작 방식

```
[호스트 폰]  유튜브뮤직 등 재생
      │  AudioPlaybackCapture (MediaProjection 동의 필요)
      ▼
  CaptureService ──┬── HTTP/WAV 스트림  :7980  → 참여자 브라우저 / PlayerService
                   └── UDP 비콘        :7981  → 참여자 앱이 호스트를 자동 발견
```

- 오디오는 무압축 PCM 44.1kHz/16bit/스테레오 = **1.41 Mbps/명**. 재인코딩이 없어 원본과 비트 동일
- 전부 로컬이라 **참여자 데이터 소모 0**, 호스트가 오프라인 저장곡을 틀면 완전 오프라인 동작
- 호스트가 핫스팟(`startLocalOnlyHotspot`)을 열 수 있어 같은 Wi-Fi가 없어도 된다

## 빌드 / 설치

```bash
JAVA_HOME=~/.gradle/jdks/eclipse_adoptium-17-aarch64-os_x.2/jdk-17.0.19+10/Contents/Home \
```

## 구성

| 파일 | 역할 |
|---|---|
| `CaptureService` | 오디오 캡처 + HTTP 서버 + UDP 비콘. 클라이언트별 큐로 느린 청취자가 전체를 막지 않게 한다 |
| `PlayerService` | 참여자 네이티브 재생. 소켓을 직접 읽어 브라우저 `<audio>` 의 2~5초 버퍼를 피한다 |
| `MainActivity` | 호스트/참여자 전환, 공유 대상 앱 선택, 핫스팟 QR |

## 검증된 것

- ✅ 유튜브뮤직 · 지니 캡처됨 (스포티파이는 앱이 자체 차단)
- ✅ **화면을 꺼도 유지됨** — `Dozing` 상태에서 무결. 핵심 요구사항
- ✅ 맥·브라우저에서 실제 청취
- ✅ `addMatchingUid()` 로 **선택한 앱의 소리만** 공유 (호출하는 순간 화이트리스트가 된다)
- ✅ STA+AP 동시 동작 — 기존 Wi-Fi 를 유지한 채 핫스팟 제공
- ✅ **네이티브 청취 지연 ≈ 0.3초** (브라우저 약 2초). 앱을 권할 근거다

### 지연 내역 (실측)

| 구간 | 지연 |
|---|---|
| 캡처 청크 | 100ms |
| 네트워크 + 송신 큐 | ~0 (`net=100% drop=0`) |
| AudioTrack 버퍼 | 200ms |
| **합계** | **≈ 300ms** |

출력 버퍼는 요청한 200ms 가 그대로 잡혔다. 입력(`AudioRecord`)만 HAL 이 자르고
출력은 존중한다 — 더 줄일 여지는 있지만 언더런과 맞바꾸는 것이라 두고 있다.

기기가 하나뿐이라 **한 폰에서 호스트와 참여자를 동시에** 띄워 검증했다.
이때 공유 대상을 **재생 중인 음악 앱 하나로 한정**해야 한다. "모든 앱 허용"이면
`PlayerService` 출력을 다시 캡처해 무한 피드백이 걸린다.
원본과 복사본이 같이 나오므로 **에코 간격이 곧 지연**이고, 귀로도 교차 확인된다.

## 앱 전환 시 끊김 — 해결됨

증상은 호스트가 앱을 전환할 때 청취자 쪽에서 1~2초 끊기는 것이었다.
**폰 자체 소리는 멀쩡했다** — audioserver 는 별도 프로세스에 실시간 우선순위라
영향을 안 받기 때문이다. 즉 소리는 나고 있었고 우리만 못 받았다.

원인은 **cgroup 강등**이었다. 캡처 스레드가 포그라운드 서비스인데도 앱이
백그라운드로 가면 `cpuset:/moderate` + `cpu:/background` 로 떨어진다(실측 89%).
그 상태에서 최근앱 전환 애니메이션이 CPU 를 몰아 쓰면 스레드가 1~2초 스케줄을
못 받고, 링버퍼가 넘쳐 그 구간 오디오가 영구히 사라진다.

**해법은 볼륨 0짜리 무음 `AudioTrack` 을 계속 재생하는 것.**
시스템은 "포그라운드 서비스인가"가 아니라 **"실제로 오디오를 출력 중인가"** 로
CPU 대우를 정한다. 소리를 받기만 하고 내지 않으면 일반 백그라운드 앱 취급이다.

| 지표 | 전 | 후 |
|---|---|---|
| 캡처 유실 | 6~10건 | **0건** |
| 최저 `cap` | 9% | **97%** |
| cgroup | background 89% | **foreground 100%** |

### 먼저 시도했다가 실패한 것 (다시 하지 말 것)

| 시도 | 결과 |
|---|---|
| 링버퍼 0.5초 → 3초 | HAL 이 **69ms 로 잘라버림**. `setBufferSizeInBytes` 는 이 경로에서 무의미하다 |
| `THREAD_PRIORITY_URGENT_AUDIO` | nice 는 제대로 걸리지만(`prio=1` 확인) **cgroup `cpu.shares` 가 상위 제약**이라 안 풀린다 |
| ADPF 성능 힌트 (API 31+) | 세션 등록은 되나 스톨 그대로 |
| FGS 타입에 `mediaPlayback` 추가 | cgroup 변화 없음 |

셋 다 엉뚱한 손잡이였다. 버퍼 크기는 `getBufferSizeInFrames()` 로 **실제 잡힌 값을
반드시 확인**해야 한다 — 요청값만 믿으면 없는 여유를 있다고 착각한다.

### 진단 방법

logcat 태그 `LT` 한 줄에 네 지점이 다 나온다:

```
AUDIO rms=12079 peak=30613 clients=1 gap=1058ms cap=9% fill=0%  net=9% drop=0  <<< 캡처 유실
                                                      │      │      │      └ 우리 큐가 버린 청크
                                                      │      │      └ 실제로 소켓에 나간 양
                                                      │      └ 끼워넣은 무음
                                                      └ 캡처가 읽은 양 (기대치 대비)
```

| cap | net | drop | 범인 |
|---|---|---|---|
| <100% | — | — | 캡처 유실 (스레드가 밀림 → cgroup 확인) |
| 100% | <100% | >0 | 송신 큐 (네트워크가 못 따라감) |
| 100% | 100% | 0 | 폰은 무죄 — 브라우저 `<audio>` 버퍼 |

cgroup 은 이렇게 본다:

```bash
PID=$(adb shell pidof com.example.lt)
TID=$(adb shell "grep -l lt-capture /proc/$PID/task/*/comm" | sed 's|/comm||;s|.*/||')
adb shell cat /proc/$PID/task/$TID/cgroup
```

**귀로 판단하지 말 것.** 무음이 나와도 "캡처 차단"과 "재생 멈춤"이 구분되지 않는다.

`fill` 은 밀린 만큼 무음을 끼워넣어 스트림의 시간을 보존하는 안전망이다.
사라진 소리는 못 살리지만, 시간까지 사라지면 받는 쪽 `<audio>` 가 언더런으로
재버퍼링에 들어가 1초 구멍이 몇 초 버벅임이 된다. 현재는 발동하지 않는다.

## 한계

- **호스트는 안드로이드 전용.** iOS 에는 시스템 오디오 캡처 API 가 없다
- MediaProjection 동의가 매 세션 필요하다. 토큰은 프로세스에 묶여 있어 저장할 수 없다
- 동의 창이 "화면 공유"를 말한다. 화면은 쓰지 않지만 안드로이드가 오디오 캡처에도 같은 동의를 요구한다
