# 인계 문서 — iOS 호스트 검증

다른 맥북에서 이어받는 에이전트를 위한 문서다. **읽는 순서는 이 문서 → `ios/README.md` → 코드.**

---

## 1. 딱 하나만 답하면 된다

> **ReplayKit 의 `audioApp` 이 유튜브뮤직 같은 "다른 앱"의 소리를 주는가?**

`ios/` 전체가 이 질문 하나를 위한 도구다. 제품이 아니다. UI 에 공들이지 마라 —
답이 "아니오"면 전부 버린다.

### 왜 아직 모르는가

"AVPlayer · 사파리 영상 · 음악 앱은 `audioApp` 에서 제외된다"는 말이 널리 퍼져 있다.
출처를 끝까지 따라가면 **Twilio 의 ReplayKit README 하나**로 수렴한다. iOS 12~14 시절
문서고, 최신 글들은 그걸 재인용만 하고 있다. **애플 공식 문서에는 그런 제외 조항이 없다.**

즉 현재 상태는 이렇다:

- ❌ "iOS 에 시스템 오디오 API 가 없다" — **틀린 말이다.** `RPSampleBufferType.audioApp` 이 있다
- ❌ "확실히 막혀 있다" — 근거가 오래된 2차 출처뿐이다
- ✅ **"API 는 있는데 우리 용도로 되는지 아무도 확인한 적이 없다"**

참고로 macOS 14.2+ 의 Core Audio process tap
(`AudioHardwareCreateProcessTap` / `CATapDescription`)은 **macOS 전용**이다.
iOS 에는 없다. ReplayKit 이 iOS 의 유일한 경로다.

## 2. 현재 상태 — 아무것도 실행되지 않았다

원래 맥북에 **Xcode 가 없어서**(CommandLineTools 만 있음) 빌드 자체를 못 했다.

| 항목 | 상태 |
|---|---|
| 소스코드 | ✅ 전부 작성됨 |
| `Shared` · `Server` · `Beacon` · `PCM` 타입 체크 | ✅ 통과 (macOS SDK, `swiftc -typecheck`) |
| `SampleHandler` · `HostViewController` | ⚠️ **미검사** — ReplayKit/UIKit 이라 iOS SDK 필요 |
| 빌드 | ❌ 안 해봄 |
| 실기기 실행 | ❌ 안 해봄 |

**첫 빌드에서 컴파일 에러가 날 수 있다.** 그건 예상된 일이고, 고치면 된다.
설계가 틀린 게 아니라 눈으로만 쓴 코드라 그렇다.

## 3. 할 일

```bash
brew install xcodegen
cd <repo>/ios
xcodegen                      # project.yml → ListenTogether.xcodeproj
open ListenTogether.xcodeproj
```

Xcode 에서 **두 타겟 모두**(`LTHost`, `LTBroadcast`) Signing & Capabilities 에서
Team 을 Apple ID 로 지정한다. 무료 계정으로 된다(7일마다 재설치).

번들 ID 를 바꿔야 하면 **확장은 반드시 `<앱ID>.broadcast`** 로 맞춘다.
`HostViewController.preferredExtension` 과 다르면 **피커 목록에 우리 확장이 아예 안 뜬다.**
이게 가장 흔한 첫 실패다.

### 실기기가 필수다

시뮬레이터로는 **불가능하다.** 두 가지 이유 다 치명적이다.

- App Store 가 없어 유튜브뮤직을 못 깐다 → **애초에 캡처할 소리가 없다**
- Broadcast Upload Extension 이 시뮬레이터에서 동작하지 않는다

## 4. 검증 절차

1. 아이폰에 설치 → 실행 → **로컬 네트워크 권한 허용**
2. **유튜브뮤직을 먼저 재생한다** ← 빼먹기 쉽다. 낼 소리가 있어야 한다
3. 앱으로 돌아와 방송 버튼 → 우리 확장 선택 → 시작 (3초 카운트다운)
4. 맥에서 로그를 본다

```bash
xcrun devicectl list devices
log stream --device --predicate 'subsystem == "com.example.lt"' --info
```

## 5. 판정 — 귀가 아니라 로그로 한다

**이건 타협하지 마라.** 무음이 들려도 "캡처가 막힌 것"과 "재생이 멈춘 것"이
귀로는 구분되지 않는다. 안드로이드 작업에서 이 함정에 여러 번 빠졌고, 그때마다
엉뚱한 곳을 고치느라 시간을 날렸다.

```
AUDIO buf=51 rms=12079 peak=30613 clients=1 drop=0 fmt=44100Hz 2ch float planar
```

| 로그 | 판정 | 다음 행동 |
|---|---|---|
| `rms` 가 0 보다 크게 요동 | ✅ **된다** | 브라우저로 실제 청취까지 확인 |
| `buf` 는 오는데 `rms=0` 고정 | ❌ 버퍼만 주고 내용이 빔 = 막힘 | 다른 앱(사파리 영상 등)으로도 한 번 더 확인 후 결론 |
| `AUDIO` 줄이 아예 없음 | ❌ `audioApp` 자체가 안 옴 | `processSampleBuffer` 에 브레이크포인트 |
| `방송 시작` 도 안 뜸 | 확장이 안 붙음 | 번들 ID · `preferredExtension` 확인 |

`rms` 가 살아 있으면 맥 브라우저에서 `http://<아이폰IP>:7980` 을 연다.
주소는 앱 화면에 전부 떠 있다.

**`fmt=` 를 반드시 확인하라.** 포맷 가정이 틀리면 `rms` 가 0 이거나 잡음이 된다 —
"막혔다"고 오판하기 딱 좋은 자리다.

## 6. 알고 있는 위험

| 위험 | 현재 대응 | 미검증 |
|---|---|---|
| 확장 메모리 **50MB** jetsam 한도 | 링버퍼 없이 즉시 흘려보냄, 클라이언트 큐 5초 제한 | 장시간 |
| 로컬 네트워크 권한을 확장이 못 띄움 | 앱 본체가 실행 시 probe 를 쏴서 미리 유발 | **이 가정 자체** |
| 포맷이 기기마다 다름 (Float/Int, 44.1k/48k, planar/interleaved) | 전부 수용 + 리샘플, 첫 버퍼 포맷 로그 | 실제 값 |
| 사파리가 무한 스트림 거부 | `Range` → **206 + 거대 Content-Range** | 실제 사파리 |
| Audio Unit 금지 (확장 내) | 안 씀. 수동 변환만 | — |

## 7. 안드로이드판과의 관계

**포트 · PCM 포맷 · 비콘 페이로드를 전부 맞춰놨다.** iOS 호스트가 동작하면
기존 클라이언트(브라우저 페이지, 안드로이드 앱)가 **한 줄도 안 고치고 붙는다.**

| 항목 | 값 |
|---|---|
| 스트림 | TCP `:7980`, `GET /stream` → WAV |
| 비콘 | UDP `:7981`, `LT1\|모델명\|IP` 를 1초마다 |
| PCM | 44100Hz / 16bit / 스테레오 / 리틀엔디안 |

### 역이식할 것 (TODO)

iOS 서버에는 **`Range` 요청에 `206` 으로 답하는 처리**가 들어 있는데
(`ios/LTBroadcast/Server.swift` 의 `handle(fd:)`), **안드로이드판에는 없다.**
`CaptureService.handleClient()` 는 `Range` 를 완전히 무시하고 항상 `200` 을 준다.

사파리는 미디어에 `Range: bytes=0-` 를 보내고 `206` 을 기대하는 성향이 강하다.
**아이폰이 안드로이드 호스트의 소리를 못 받는다면 1순위 용의자가 이것이다.**

## 8. 제품 맥락 — 되더라도 끝이 아니다

이 앱의 유일한 경쟁력은 **저마찰**이다. "이어폰 한쪽 나눠 끼기"를 대체하는 게
목표라서, 준비가 번거로우면 그냥 이어폰을 나눠 낀다.

`audioApp` 이 된다 해도 iOS 호스트에는 이게 남는다.

- 매 세션 `RPSystemBroadcastPickerView` → **3초 카운트다운**
- 심사 통과 여부 불명 (타 앱 오디오를 네트워크로 내보내는 것)

안드로이드는 동의창 한 번이다. 그래서 **호스트 = 안드로이드**라는 제품 결정은
이 검증 결과와 무관하게 유지될 가능성이 높다. 이 검증의 값어치는
"안 되는 걸 확인해서 미련을 끊는 것" 또는 "된다면 선택지를 하나 더 갖는 것"이다.

**아이폰은 청취자로 쓰는 게 주 경로다.** 그쪽이 더 급하다 (루트 `README.md` 의 미검증 항목).

## 9. 작업 규칙

- **커밋 · 푸시는 사용자가 명시적으로 요청할 때만** 한다
- 커밋 메시지에 `Co-Authored-By` 를 넣지 않는다
- 에러 로그만 받으면 바로 고치지 말고 **원인 분석 + 수정 계획을 먼저 보고**한다
- 추측으로 "됐다"고 말하지 않는다. 안드로이드에서 `setBufferSizeInBytes(3000ms)` 가
  실제로는 `69ms` 로 잘려 있었고, 요청값만 믿다가 한참을 헤맸다.
  **실제로 잡힌 값을 로그로 확인하고 말하라.**
